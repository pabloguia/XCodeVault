## F1. Where the simulator gigabytes actually live (this invalidates the naive model)

- `/Library/Developer/CoreSimulator/Profiles/Runtimes/*.simruntime` is **largely a mount
  graft, not storage**. Since Xcode 14 a downloaded runtime is a disk image mounted so
  its internal `Library/Developer/CoreSimulator/Profiles/Runtimes/...` hierarchy is
  surfaced at the canonical path. **[COMMUNITY-REPRO]**
  https://macops.ca/xcode-14-new-platforms-packaging-format/ (2022-09) ·
  https://theapplewiki.com/wiki/Simulator_Runtime_MobileAssets (updated 2026-07-14)
- The daemon **`simdiskimaged`** manages those mounts under
  `/Library/Developer/CoreSimulator/Volumes/<Platform>_<Build>`. Manually unmounting
  them makes Xcode lose the runtimes while `simctl runtime list` still reports "Ready."
  **[COMMUNITY-REPRO]** (same macops.ca source; real Xcode 16/26-era paths in
  https://github.com/dotnet/xharness/issues/1278 and
  https://github.com/eloybasado/xcode-phantom-runtime-fix)
- Directory is **`Cryptex` (singular)**: `Cryptex/Images/Inbox/<UUID>.dmg` for downloads
  in flight, `Cryptex/Images/bundle/SimRuntimeBundle-<UUID>` for the installed bundle.
  No evidence of a `Cryptexes` or `Images/Bundles` path — naive path constants will miss.
  **[COMMUNITY-REPRO]**
- **A large share of "Xcode disk usage" is outside `/Library/Developer` entirely**:
  `/System/Library/AssetsV2/com_apple_MobileAsset_iOSSimulatorRuntime/<sha1>.asset`.
  Despite the `/System` prefix this is a separate mount point and is read/write.
  Gui Rambo reclaimed ~30 GB there. **[COMMUNITY-REPRO]**
  https://mastodon.social/@_inside/112904004439494121 (2024-08-04)
  → **Any scanner that walks only `/Library/Developer` and `~/Library/Developer` will
  systematically under-report.** Conflicting reports exist on whether individual assets
  there are deletable (SIP/held-open); unresolved. **[UNKNOWN]** GATING.
- Runtime images are **sealed and hash-verified** (AEA-encrypted Apple Archive
  containing `iOSSimulatorRuntime_Cryptex.dmg` + `.trustcache` + `.root_hash`), mounted
  as APFS volumes on synthesized containers, invisible to `mount(8)`. Failure surfaces
  as `SimDiskImageErrorDomain Code 5` / `-67061 invalid signature`. **[COMMUNITY-REPRO]**
  https://developer.apple.com/forums/thread/803217
  → A **byte-identical** copy on another volume *might* still validate; nobody has
  published such a test. **[UNKNOWN]** GATING.
- Apple DTS (Ed Ford): these are "mounted as APFS volumes on synthesized containers";
  manage them with `xcrun simctl runtime list/delete` or Xcode Settings ▸ Components;
  ***"Don't use Disk Utility to manage these installations or mount points."***
  **[APPLE-STAFF]** https://developer.apple.com/forums/thread/818405
- `NeverCollected` MobileAssets create real orphans that neither Xcode nor `simctl` can
  remove. Any relocation scheme risks manufacturing more of these.
  **[COMMUNITY-REPRO]** https://developer.apple.com/forums/thread/812992

## F2. Apple's officially supported relocation surface is narrow — and documented

- Apple DTS (Quinn) position: only **Derived Data, Archives, and the Compilation Cache**
  are safely relocatable (Xcode ▸ Settings ▸ Locations). Simulator runtimes are the big
  burden and the advice is to *delete* all but one. There is **no Apple-endorsed
  relocation mechanism for CoreSimulator.** **[APPLE-STAFF]**
  https://developer.apple.com/forums/thread/818884
- Documented component flags (verbatim from Apple's "Downloading and installing
  additional Xcode components", current 2026): **[APPLE-DOC]**
  https://developer.apple.com/documentation/xcode/downloading-and-installing-additional-xcode-components
  ```
  xcodebuild -downloadPlatform <iOS|watchOS|tvOS|visionOS> \
    [-exportPath <dir> -buildVersion <osversion> -architectureVariant <universal|arm64>]
  xcodebuild -downloadAllPlatforms [-exportPath <dir>]
  xcodebuild -importPlatform "~/Downloads/watchOS 9 beta Simulator Runtime.dmg"
  xcodebuild -runFirstLaunch -checkForNewerComponents
  xcodebuild -downloadComponent metalToolchain [-exportPath ~/Downloads]
  xcodebuild -importComponent metalToolchain ~/Downloads/metalToolchain.dmg
  ```
  - `-exportPath` + `-importPlatform` is **Apple's blessed "keep installers elsewhere,
    install offline" path** — exactly the Runtime Library concept, and it is supported.
  - `-architectureVariant arm64` avoids the fat Intel image: **materially smaller
    download and install**. This is free savings the original brief missed.
  - `-checkForNewerComponents` stores files in **`~/Library/Developer/Packages/`** — an
    Apple-documented cache directory essentially no cleanup tool knows about.
  - `-downloadComponent`/`-importComponent`/`-showComponent` are **Xcode 26** (Metal
    toolchain is no longer in the default install).
  - Known bugs to feature-detect around: `-buildVersion` rejected as an invalid option
    in some Xcode 16/26 builds; `-downloadPlatform` reports "all downloaded" on CI; it
    does not honour proxy settings. **[COMMUNITY-REPRO]**
- DerivedData defaults keys `IDECustomDerivedDataLocation` / `IDEBuildLocationStyle` are
  from a **2016** source; not confirmed current for Xcode 16/26. Verify empirically
  before writing them. **[UNKNOWN]**
- `xcrun simctl --set <path>` (alternate device set) **exists but is undocumented by
  Apple**; Simulator.app honours it via `--args -DeviceSetPath`; **no evidence the Xcode
  IDE run-destination picker honours it**, and simulators in a custom set do **not**
  appear in Safari's Web Inspector. Not a viable foundation for transparent relocation.
  **[COMMUNITY-REPRO]** https://developer.apple.com/forums/thread/717733

## F3. Symlink indirection is worse than the brief assumed — it breaks things on-disk too

- **Whole-`~/Library/Developer` symlink breaks Xcode 15+ physical-device DDI discovery.**
  Reproduced on Xcode 15.0 / 15.1 / 15.3; filed as **FB12363725**. Published workaround
  gives a precise allowlist: keep `~/Library/Developer` a **real directory**, then
  symlink individual children — `CoreDevice`, `CoreSimulator`, `RemotePairing`, `Shared`,
  `XCPGDevices`, `XCTestDevices`, `Xcode` — and **`~/Library/Developer/DeveloperDiskImages`
  must stay a real directory.** **[COMMUNITY-REPRO]**
  https://developer.apple.com/forums/thread/731650
- **But symlinking `~/Library/Developer/CoreSimulator` alone also breaks the Simulator** —
  Jeff Johnson (Lapcat), 2025-08-17: with that directory symlinked to another path *on
  the same internal disk*, the iOS Simulator's Files app could not share, save, or create
  folders. Fix was removing the symlink. **The breakage is caused by the indirection
  itself, not by the external drive.** **[COMMUNITY-REPRO]**
  https://lapcatsoftware.com/articles/2025/8/5.html
  → This is the exact symlink `mac-ssd-rescue` creates, and it invalidates the
  "per-category symlink is the safe fallback" assumption for CoreSimulator specifically.
- Relocating the **system-domain** `/Library/Developer/CoreSimulator`: a 2019 Apple
  engineer comment claimed Xcode 11 could find runtimes on any attached disk; **users
  attempting it in 2021, 2022, and Oct 2024 (Sonoma 14.6 + Xcode 16, symlink and alias
  both) all failed.** No working recipe has ever been posted.
  **[COMMUNITY-REPRO]** https://developer.apple.com/forums/thread/117141

## F4. External volumes have a sandbox/TCC problem that hits even Apple's supported path

- **Apple's own supported DerivedData relocation breaks framework tests when the target
  is on an external volume** — `xctest` cannot load the test bundle from `/Volumes/...`,
  apparently a sandbox restriction. Reported **January 2026**, zero replies.
  **[COMMUNITY-REPRO]** https://developer.apple.com/forums/thread/812321
- macOS has a distinct **"Files and Folders ▸ Removable Volumes"** TCC category with
  **no API to preflight or request it**. **[COMMUNITY-REPRO]**
  https://developer.apple.com/forums/thread/686498
- **The decisive open question: does TCC/sandbox classify by device removability or by
  `/Volumes` path?** If by removability, then mounting the external volume at a canonical
  path does *not* escape the problem, and much of the canonical-mount thesis collapses.
  **[UNKNOWN]** GATING — highest-value single experiment in this document.

## F5. Mount mechanics — what is actually available

- `mount_apfs(8)` / `diskutil mount -mountPoint <path> <UUID>` can mount at an arbitrary
  existing directory; `diskutil` accepts a **volume UUID**, which is what survives
  `/dev/diskN` renumbering on external disks. Root required; no entitlement exists or is
  needed for an unsandboxed root daemon. **App Sandbox** is what blocks mounting
  (`system.volume.external.mount` authorization right). **[APPLE-DOC]/[APPLE-STAFF]**
  https://keith.github.io/xcode-man-pages/mount_apfs.8.html ·
  https://developer.apple.com/forums/thread/775835
- **Ownership hazard:** external volumes default to *ownership ignored* (`noowners`,
  everything uid/gid 99). CoreSimulator content has mixed root/user ownership — mount
  with `owners`, and/or `mount_apfs -u/-g`, `diskutil enableOwnership`. **[APPLE-DOC]**
- **Known-good production pattern (Nix `/nix` store):** fstab
  `UUID=… <path> apfs rw,noauto,nobrowse,nosuid,noatime,owners` (fstab as *suppressor*,
  not as the mounter) + a root **LaunchDaemon** doing `diskutil mount -mountPoint`.
  Nix deliberately does **not** rely on fstab to perform the mount. **[COMMUNITY-REPRO]**
  https://github.com/NixOS/nix/blob/master/scripts/create-darwin-volume.sh
  → Caveat: Nix's volume is in the **internal** container, so it is always present at
  boot. The disk-absent problem — our hardest problem — does not exist for Nix.
- Apple DTS recommends **`StartOnMount`** LaunchDaemons + **Disk Arbitration** for
  "wait for external disk", and **`getattrlist(2)` with `ATTR_DIR_MOUNTSTATUS`**
  (`DIR_MNTSTATUS_MNTPOINT`) as the cheap, race-free "is something mounted here?" check —
  explicitly preferred over Disk Arbitration for synchronous decisions. **[APPLE-STAFF]**
  https://developer.apple.com/forums/thread/786316 ·
  https://developer.apple.com/forums/thread/776198
- `DARegisterDiskMountApprovalCallback` can **veto** the default `/Volumes/...` mount so
  we can remount at the canonical path ourselves (fstab `noauto` achieves the same more
  simply). **[APPLE-DOC]**
- **`/etc/synthetic.conf` is not applicable** — root-level entities only; both target
  paths are nested. Worth noting only because its synthetic empty directories are
  *un-writable*, which is exactly the shadow-data protection we wish we had. **[APPLE-DOC]**
- **APFS firmlinks are not available to third parties** (no API, no tools, undocumented).
  Hard links can't cross volumes and APFS has no directory hard links. Finder aliases are
  invisible to POSIX. All dead ends. **[COMMUNITY-REPRO]**
- **`mount_nullfs` requires SIP + AMFI disabled** → excluded by our safety rules.
  **macFUSE/bindfs requires a kext** → on Apple Silicon that means a recoveryOS Reduced
  Security downgrade → excluded. **[APPLE-DOC]/[COMMUNITY-REPRO]**
- **FSKit (the genuinely new option the brief never considered):** Apple ships an official
  **passthrough file system sample** — `FSPathURLResource`, mounted with a plain
  `mount -t <yourfs> <src> <dst>`. First-party, kextless, notarizable, no SIP change.
  Framework macOS **15.4+**; the passthrough sample is **macOS 26.0+**. Requires the
  `com.apple.developer.fskit.fsmodule` entitlement (appears approval-gated) and the user
  must manually enable the extension in Login Items & Extensions. The sample omits
  xattr operations and kernel-offloaded I/O — both of which a CoreSimulator-backing
  filesystem would need. Performance unmeasured. **[APPLE-DOC]**
  https://developer.apple.com/documentation/FSKit/building-a-passthrough-file-system
  → Strategically the right long-term answer; tactically premature. Track as an R&D tier.

## F6. Disconnect / split-brain — confirmed as the core risk, with a partial defense

- Expected sequence on surprise removal: mount torn down → canonical path resolves to the
  **ordinary empty local directory** → Xcode/`simdiskimaged` recreates content on the
  **internal** disk → on reconnect the mount either fails (non-empty mount point) or
  succeeds and **silently hides** the local data, which then consumes internal disk
  invisibly. **Inference from VFS semantics; not sourced for APFS surprise-removal.**
  **[UNKNOWN]** GATING.
- Compounding factor: CoreSimulator runtimes are **nested mounts** under `Volumes/`.
  Surprise removal tears down a *tree*, leaving `simdiskimaged` with a database pointing
  at vanished images — expect zombie runtime state, not merely missing files.
- No published macOS shadow-data detection pattern exists. Usable primitives:
  `ATTR_DIR_MOUNTSTATUS`, `statfs(2)` `f_mntfromname`/`f_fsid`, LaunchDaemon `WatchPaths`
  as a tripwire, and a **sentinel file at the volume root** to distinguish "mounted" from
  "local directory that happens to have content."
- Candidate defense (**our synthesis, unverified**): keep the unmounted mount point
  `chflags uchg`, mode `0500`, root-owned so stray writes fail loudly instead of
  silently succeeding. Must be tested against how `simdiskimaged` reacts to `EPERM` —
  it may crash Xcode in a worse way. GATING.

## F7. Privileged helper — the modern shape, and the vulnerability class to avoid

- **`SMJobBless` is deprecated as of macOS 13.** `SMAppService` is macOS 13.0+, and
  **only `SMAppService.daemon` runs as root** (`.agent` runs as the user). The launchd
  plist lives at `YourApp.app/Contents/Library/LaunchDaemons/<name>.plist`; pass the
  **full filename including `.plist`** to `daemon(plistName:)`; use `BundleProgram`
  (bundle-relative) and `AssociatedBundleIdentifiers`; do **not** carry over
  `SMPrivilegedExecutables`/`SMAuthorizedClients`. Registration lands in
  `.requiresApproval` until the user enables it in **Login Items & Extensions**; a daemon
  additionally requires admin authentication. Debug with `sfltool dumpbtm`.
  **[APPLE-DOC]/[APPLE-STAFF]** https://developer.apple.com/forums/thread/725811
- **Client validation:** use **`NSXPCConnection.setCodeSigningRequirement(_:)`** (macOS
  13+) or `xpc_connection_set_peer_code_signing_requirement` (macOS 12+), set **before
  `resume()`**. Apple DTS: these perform real certificate-chain validation and you should
  **not hand-roll `SecCodeCheckValidity`** (TOCTOU exposure). **[APPLE-STAFF]**
  https://developer.apple.com/forums/thread/773573
- **Never** validate by PID (`processIdentifier` → `SecCodeCopyGuestWithAttributes`) —
  PID reuse + exec race is the classic escalation. **[COMMUNITY-REPRO]**
- Concrete cautionary CVE: **CVE-2025-65842** (Acustica Audio HelperTool) — accepted every
  connection, called `AuthorizationCopyRights(NULL, …)`, then passed attacker-controlled
  arguments to an exec API → any local user to root. The root cause is *a helper that can
  run arbitrary commands*. Our allowlisted-verb design exists to make that impossible.
  **[COMMUNITY-REPRO]** https://almightysec.com/helpertool-xpc-service-local-privilege-escalation/
- **A root launchd daemon does not need Full Disk Access** (TCC is a user-level concept).
  The **GUI app** running as the user will hit TCC enumerating `~/Library`. Split the work
  accordingly. Whether `~/Library/Developer` specifically is TCC-protected on macOS 26/27
  is **[UNKNOWN]** — test on a clean VM.
- Distribution: Developer ID for app *and* helper, inside-out signing, hardened runtime,
  `--timestamp`, notarize the container (not the bare helper), `stapler staple` the
  .app/.dmg/.pkg, strip `com.apple.quarantine` xattrs before signing (Apple requirement
  since 2025-02-18). Homebrew Cask is viable (`uninstall launchctl:`, `zap`), but
  `brew uninstall` deleting the bundle leaves a **stale BTM entry** — ship an in-app
  uninstall that calls `unregister()`. **[APPLE-DOC]/[COMMUNITY-REPRO]**
- No widely-audited open-source SMAppService **root daemon** reference exists. Closest
  material: `alienator88/HelperToolApp` (mechanics only — its arbitrary-command design is
  the anti-pattern), `trilemma-dev/SwiftAuthorizationSample` + `SecureXPC` (security
  reasoning, SMJobBless-era), `securing/SimpleXPCApp` (archived, teaching), and Apple's
  own sample which is **agent-only, not a root daemon**.

## F8. Legacy support — the 10.13 target is not defensible

- Xcode → minimum macOS (to run): Xcode 15 → macOS 13.5 · Xcode 16 → macOS 14.5 ·
  **Xcode 26 → macOS 15.6** (Apple release notes, **[APPLE-DOC]**) · Xcode 26.4 → macOS
  26.2 **[WEAK]**.
- **Since 2026-04-28 App Store Connect requires builds made with Xcode 26.** Therefore
  *any developer still shipping to the App Store is already on macOS 15.6+.* **[APPLE-DOC]**
  https://developer.apple.com/news/upcoming-requirements/
- macOS support status (Sept 2026): 27 expected mid-Sept 2026; 26 and 15 supported;
  **14 reaching EOL ~Sept 2026**; 13 and older unsupported. **[COMMUNITY-REPRO]**
- **CI reality: GitHub-hosted `macos-13` runners are gone (fully unsupported 2025-12-04)
  and `macos-14` is fully unsupported 2026-11-02.** Only `macos-15` and `macos-26`
  remain. Supporting macOS ≤14 means self-hosted Macs or untested claims. **[APPLE-DOC-equiv]**
  https://github.com/actions/runner-images/issues/13046 · .../13518
- Below macOS 13 you don't lose a feature, you gain a **second product**: a parallel
  SMJobBless implementation with its own installer/updater/uninstaller, plus hand-rolled
  audit-token validation — in the one component where a bug is local root escalation.
  Plus APFS 1.0 on 10.13 predates volume groups/firmlinks entirely.
- No credible 2026 dataset breaks down macOS version among *developers running Xcode*.
  The structural argument (App Store requires Xcode 26 requires macOS 15.6) is stronger
  than any telemetry.

## F9. Competitive landscape — the gap is real, and so is the reason for it

- **Every mature tool in this space deletes; not one relocates.** DevCleaner (~1.6k
  stars, release 2.8.0 Nov 2025, Homebrew cask, macOS 14+), ClearDisk (~590 stars, 79
  cache paths), CodePurge, xcleaner, CleanMyMac CLI (v1.0.0 beta Jul 2026), DaisyDisk,
  CleanMyMac — all delete-only.
- `Viniciuscarvalho/mac-ssd-rescue` is **3 commits, 2 stars, 0 issues, 0 releases**, a
  328-line bash script. Migration is literally `rsync -a --delete` (no `-X -A -E`, so
  **xattrs/ACLs/resource forks are dropped**), verification is `find -type f | wc -l`
  compared with `<`, then `rm -rf` + `ln -s`. stderr is discarded. No free-space check,
  no destination-filesystem check, no restore verification, **no story at all for the
  drive being absent** (README advice: "keep the USB drive connected"). It only touches
  `$HOME` paths, so it never reaches the runtimes that hold the gigabytes on Xcode 15+ —
  and the CoreSimulator symlink it creates is the configuration Jeff Johnson documented
  breaking the Simulator (F3). **There is nothing here to reuse as a codebase.**
- Unmet demand is documented: XcodesApp issue #781 ("Add Storage Management Tools for
  Xcode Junk", opened 2025-12-10) still open, unanswered; the Apple forum CoreSimulator
  relocation thread runs 2019 → Oct 2024 with no working solution ever posted.
- **Nobody has published an Xcode build benchmark across storage tiers.** Adjacent data:
  Xcode startup reads 207 MB over 13 s dominated by **4 KB–64 KB operations** — these
  workloads are bound by **random 4K IOPS at low queue depth, not sequential MB/s**;
  a cheap USB 3.1 enclosure measured ~210 MB/s. Internal M1 ~6.5–7.5 GB/s vs Thunderbolt
  ~1.5–2.6 GB/s. **[COMMUNITY-REPRO]**
  https://www.michaelstinkerings.org/the-macos-storage-speed-myth-part-1-decoding-ssd-benchmarks-and-real-world-file-operations/ ·
  https://eclecticlight.co/2022/04/28/are-thunderbolt-ssds-more-consistent-than-usb/
  → Drive qualification must measure **4K random IOPS at QD1–4**, not sequential
  throughput. Publishing this benchmark is a cheap, real differentiator.
- **Install-time trap:** installing a runtime reportedly needs **~40 GB free** even though
  the installed runtime is 9–12 GB, and staging happens on the internal volume.
  Relocation alone does not solve the user's most acute moment of pain unless staging is
  handled too. **[COMMUNITY-REPRO]** https://developer.apple.com/forums/thread/732407

### F1 corrections — where the bytes are on Xcode 26.5

- **`/Library/Developer/CoreSimulator/Cryptex/Images/bundle` is empty** on this install. Both
  installed runtimes are `kind = "Patchable Cryptex Disk Image"` whose `path` is
  `/System/Library/AssetsV2/com_apple_MobileAsset_<platform>SimulatorRuntime/<sha1>.asset/AssetData/Restore/<Platform>SimulatorRuntime_Cryptex.dmg`.
  **100 % of installed-runtime bytes (15.8 GB) live in the MobileAsset store**, zero under
  `/Library/Developer/CoreSimulator`. The desk finding that "a large share" is in AssetsV2
  under-stated it for current Xcode: on 26.5 it is all of it.
- The runtime images are **visible to `mount(8)` and `hdiutil info`** (as `/dev/diskN`
  attachments of the `.dmg`, mounted `apfs, sealed, read-only, nobrowse` at
  `/Library/Developer/CoreSimulator/Volumes/<Platform>_<Build>`). The desk claim "invisible to
  mount(8)" is **incorrect** for this generation.
- `/Library/Developer/CoreSimulator` itself holds **7.4 GB in `Caches/dyld`** (root-owned dyld
  shared caches built per runtime when simulators boot) — the only large regular storage there.
  `Profiles/` is 5 MB of device-type definitions. `Images/` (not `Cryptex/Images`) holds
  `images.plist` (the runtime registry) plus empty `Inbox`/`mnt`.
  **⚠ Both bullets above are contradicted by a later observation — see "A runtime installed by
  `-importPlatform` does not live in the MobileAsset store" at the end of this file (2026-09-08).**
  They remain accurate for a runtime Apple downloaded; they are wrong as a general statement.
- `xcrun simctl runtime` on Xcode 26.5 has verbs **`add <path> [--move] [--async]`** ("the image
  will be staged, verified, and mounted; when possible the image file will be cloned so no
  additional disk space is used"), **`delete (<id>|--notUsedSinceDays N) [--dry-run] [--keep-asset]`**,
  **`unmount`**, **`verify`**, `list`, `match list/set`. `--keep-asset` and the clone-on-add
  behaviour matter for the Runtime Library design (add from an external volume cannot clone
  across volumes → a full copy into the MobileAsset store is unavoidable; E11).

### F4/H6 — the external-volume xctest failure reproduced, and it follows the physical device (E2)

`xcodebuild test -destination platform=macOS -derivedDataPath <X>` with a dynamic-library +
XCTest fixture (`fixtures/E2Fixture`):

| DerivedData location | DiskArbitration class | xcodebuild test | swift test |
|---|---|---|---|
| internal Data volume | Internal/Fixed | pass | pass |
| **real USB SSD, `/Volumes/<name>/…`** (Case-sensitive APFS, owners on) | External/Fixed | **FAIL** | pass |
| internal path that is a **symlink** to the USB SSD | External/Fixed | **FAIL** | pass |
| APFS disk image at `/Volumes/<img>` | External/Removable | pass | pass |
| same disk image at `$HOME/<dir>` | External/Removable | pass | pass |
| **case-sensitive** APFS disk image at `/Volumes` | External/Removable | pass | pass |
| disk image, hidden `.TemporaryItems/folders.<uid>/…` path (mirrors the USB path) | External/Removable | pass | pass |
| disk image attached with **ownership enabled** (`-owners on`) | External/Removable | pass | pass |
| disk image whose **backing file lives on the USB SSD** (I/O goes through the USB device) | External/Removable | pass | pass |

Failure text, verbatim: `xctest (<pid>) encountered an error (Failed to create a bundle instance
representing '/Volumes/<name>/…/Build/Products/Debug/E2LibTests.xctest'. Check that the bundle
exists on disk.)` — the bundle does exist and `swift test`'s `xctest` loads it from the same
path. So: **not the `/Volumes` path, not case sensitivity, not the hidden path, not
DiskArbitration's External/Removable classification, not ownership handling, not the USB I/O
path** (a disk image stored on the USB SSD passes). The discriminator is the **physical
external volume as such** — a property only physical volumes have; TCC's "Removable Volumes"
category remains the prime suspect, but unified-log queries for TCC/sandbox denials during
the failing run returned nothing, so the mechanism is **still unnamed [UNKNOWN]**. A
canonical mount path would not escape it: the symlink case shows the check follows the real

### E8 import half + E11 (import) — `-importPlatform` copies the image internally first (2026-09-06)

`scripts/experiments/e8c-import-roundtrip.sh <bundle>` with 10.3 GB free internally:

**E12 — case-sensitive APFS is not the hazard the qualification warning implied (2026-09-08,
macOS 26.6.2 25G83 / Xcode 26.5 17F42 / Intel):** `VolumeQualification` shipped a warning that
"Xcode projects that rely on case-insensitive paths may break" on a case-sensitive volume. It was
written from first principles and had never been tested, yet it gates a real decision: the user's
actual destination drive is Case-sensitive APFS. Tested on a disposable `hdiutil` sparse image (no
sudo, drive untouched), with a control first to prove the two volumes genuinely differ — `probe.txt`
and `PROBE.txt` coexist on the case-sensitive one and collapse into a single file on the internal
one, the second write silently winning. Both product-shaped workloads then passed: a full
`swift build --scratch-path` on the case-sensitive volume (which also clones dependency *source*
into `checkouts/` — the riskier half, since a package with case-inconsistent internal references
breaks when its source is case-sensitive, not when its output is), and an
`xcodebuild -derivedDataPath` build with source left on the internal volume. The warning is now
narrowed to what was measured, and the residual risk named precisely: source code that refers to a
file by the wrong case is invisible on the internal volume and a build error on a case-sensitive
one. Not tested: CocoaPods, Carthage, bridging headers, frameworks shipping case-colliding
filenames. Incidental confirmation of F5: the sparse image mounts `noowners` and `volumes`
correctly reports it `unsuitable` with the ownership blocker. **[VERIFIED-BY-US]**

**Ownership is a two-sided setting, and the second side is undocumented until you hit it
(2026-09-08):** F5 says external volumes default to `noowners` and must have ownership enabled,
because CoreSimulator/Xcode data carries mixed root/user ownership. What F5 does not say is that
enabling ownership is *also* what makes the volume root honour its real `root:wheel` ownership —
so the user can no longer create anything at the volume root, and `vault init` fails with a bare
"permission denied". The two faces are the same setting: the qualification the tool demands is what
produces the failure the user hits. Confirmed on the user's own drive (`/Volumes/<vault>`,
Case-sensitive APFS, `Owners: Enabled`, root `drwxr-xr-x root:wheel`). The same mechanism explains a
second surprise: after deleting the prior tool's data, `rm -rf` emptied the directory but could not
remove the directory itself, because unlinking an entry from the volume root needs write permission
on that root. Both need exactly one privileged step, which XCodeVault prints and never runs — see
`OwnershipAdvice`. **[VERIFIED-BY-US]**

macOS 26.6.2 25G83 / Xcode 26.5 17F42 / Intel):** F1 above states that 100 % of installed-runtime
bytes live in `/System/Library/AssetsV2/...` and that `/Library/Developer/CoreSimulator/Images/`

### F10 — a removed runtime leaves its dyld shared cache behind, and `inc/` keeps interrupted builds

Measured 2026-09-08 on macOS 26.6.2 (25G83) / Xcode 26.5 / Intel x86_64. `du -x` on
`/Library/Developer/CoreSimulator/Caches/dyld` reports 9.4 GiB, laid out as

```
dyld/<hostMacOSBuild>/<runtimeIdentifier>.<runtimeBuild>/      ← finished caches
dyld/<hostMacOSBuild>/inc/<runtimeIdentifier>[.<runtimeBuild>] ← builds in progress
```

The bracket is not hedging for its own sake: the one `inc/` entry observed here carries the build
suffix, but `inc/` and the finished level are **two naming conventions**, and confirming one says
nothing about the other. The `doctor` rule therefore claims both forms and confirms each level
separately — an earlier version confirmed the scheme once for the whole tree, which let one
platform's naming license exact matching for another and reported a live cache for deletion.

The host directory name equals `sw_vers -buildVersion` (`25G83`) — on one machine, with one value,
so this is a consistent reading of the layout and not evidence about the naming scheme. Finished
caches carry `dyld_sim_shared_cache_x86_64[.NN]` plus a `.atlas`, all mode 0644.

**The finding:** `inc/com.apple.CoreSimulator.SimRuntime.tvOS-26-5.23L470` held **2.3 GiB** for a
runtime that is *not installed* — `simctl runtime list` reports only iOS 26.5 and watchOS 26.5, and
there is no tvOS `.dmg` under `Images`. (An earlier draft also cited the absence of a tvOS bundle
under `Profiles/Runtimes`; that directory does not exist on this machine at all, so the observation
was vacuous rather than corroborating. `Profiles/` holds only `DeviceTypes`.) Note the assumption
this rests on: `simctl runtime list` enumerates *disk-image* runtimes, so on a machine with a
runtime bundled inside an older Xcode, absence from that list would not mean absence from the
machine. The `doctor` rule therefore also treats an available device as a witness for its runtime. It contained a
mode-0600 `dyld_sim_shared_cache_x86_64.02-alj3CU` — an `mkstemp` part file — and no `.atlas`.
*Inferred, not measured:* that the build was **interrupted** rather than failed, since
`update_dyld_sim_shared_cache-stderr.txt` holds only the routine "not placed in shared cache
because: Missing split seg info" warnings a healthy build also emits. CoreSimulator wrote inside
this tree at 07:06 the next morning, updating `inc/`'s own mtime, and did not collect the orphan.

**What has NOT been tested, and it is the thing that matters.** `kern.boottime` is Sep 7 17:39:10;
the orphan's mtime is Sep 7 18:54 — it was created *after* the last boot and has never been through
a restart. The analogous case in this document is unambiguous about why that is the decisive probe:
the stranded runtime Inbox `.dmg` (2026-09-06 note above) was reclaimed by a **startup GC**, and
before that root deletion had been refused with `Operation not permitted`. So an earlier draft of
this section, which read "keeps interrupted builds forever" and "nothing reclaims it", overstated a
day of uptime as a permanent condition. Corrected: *survived the runtime's removal and several
simulator boots within one uptime session; not yet tested across a restart.*

**Privilege — and a correction worth carrying.** The tree is root-owned (`root:admin`), carries no
BSD file flags (`ls -lO` → `-` on the whole ancestor chain), and `/Library/Developer/CoreSimulator`
is absent from `/System/Library/Sandbox/rootless.conf`, which lists only `/System/Developer`. An
earlier draft concluded from exactly those two observations that "root deletion is expected to work
here". **That inference is falsified by this document's own Inbox experiment**, where the file had
*both* properties and root still got EPERM three times, with `chflags` and `lsof` ruling out flags
and open handles. That section ends with the instruction "`doctor` must not promise a root-only
fix", and the first version of the `doctor` rule broke it. The rule now leads with the restart probe
and offers only a narrow `rm -f` of the known cache filenames followed by `rmdir`, which refuses if
anything unexpected is inside.

**Next probes, in order:** (1) reboot and re-check the orphan — free, unprivileged, and gates the
whole finding; (2) only if it survives, the root deletion; (3) separately, whether a superseded
runtime *build* leaves a finished cache behind, which is the most likely orphan class on any machine
that has taken a runtime update and which no machine here has yet exhibited.

**Accounting trap re-confirmed while measuring.** `du -sh /Library/Developer/CoreSimulator` reports
33 GiB for `Volumes/` alone, which is phantom: those are the sealed read-only APFS runtime images
mounted at `Volumes/<Platform>_<Build>`, so a traversal that crosses mount points counts runtime
bytes a second time. `du -shx` reports 0 B. `DiskUsage` already handles this (`FTS_XDEV` plus a
per-directory `ATTR_DIR_MOUNTSTATUS` check) and is unaffected. **[VERIFIED-BY-US]**

### F11 — exporting an *already-installed* runtime is nearly free internally; only a download is not

E11 measured `-downloadPlatform … -exportPath` at ~7 GB peak internal use for a 5 GB image and
concluded the export "downloads, INSTALLS the runtime on the internal volume, then exports a copy".
That is the behaviour for a runtime that is **not yet installed**. For one that is, `-exportPath`
copies the sealed image out and internal use stays flat.

Measured twice — **both times without `-buildVersion`**, i.e. in the case where the latest available
build happened to be the one installed. The pinned-build path (`-buildVersion 23F77` against an
installed 23F77) is *inferred* from these, not separately measured, and the preflight says so rather
than citing these runs as if they covered it. The measurements: 1 MB peak for iOS 26.5 during the
E11 round trip
(`docs/research/evidence/e11-iOS-macos26.6.2-25G83-xcode26.5-x86_64.txt`), and again on 2026-09-08
exporting the same 10.6 GB image to an external APFS volume
(`docs/research/evidence/f11-export-installed-runtime-macos26.6.2-25G83-xcode26.5-x86_64.txt`) — 4.4 GB written to the destination in the first
20 s with internal free unchanged at 14 GiB throughout, start to finish.

This distinction was worth a code change rather than a note. The export preflight told every caller
the expensive story, which on a nearly-full disk argues the user out of the one operation that frees
the most space — export the installer to a vault, then `runtime offload`. It now branches on whether
the platform is already installed, and falls back to the expensive story when the runtime list is
empty (a failed probe must not be read as a cheap path). **[VERIFIED-BY-US]**

### F12 — `-exportPath` emits two different artifact shapes, and it tracks the backing store

Measured 2026-09-08/09, same host. `xcodebuild -downloadPlatform <p> -exportPath` produced a
**directory** for one runtime and a **file** for another:

| artifact | shape | size |
|---|---|---|
| `watchsimulator_26.5_23T570.exportedBundle` | directory (`ExportedMetadata.plist` + `Restore/`, sealed image at `Restore/WatchOSSimulatorRuntime_Cryptex.dmg`) | 5.24 GB |
| `iphonesimulator_26.5_23F77.dmg` | file | 10.6 GB |

**The controlled observation, on one runtime.** iOS 26.5 build 23F77 exported as
**`.exportedBundle`** at 2026-09-08T06:43 while MobileAsset-backed
(`evidence/e11-iOS-macos26.6.2-25G83-xcode26.5-x86_64.txt:27`), was re-installed via
`-importPlatform` three hours later (`evidence/e11-import-iOSSimulatorRuntime_Cryptex-…txt:2`,
09:45), and the same runtime at the same build exported as a plain **`.dmg`** tonight
(`evidence/f11-export-installed-runtime-…txt:36`). Platform, version and build held constant; only
the backing store changed. The watchOS row above is consistent with it but adds no independent
weight, since it varies platform and provenance together.

**Mechanism inferred, not observed.** Nothing measured Xcode branching on the backing store; what is
measured is that the shape *correlates* with it, with the confound removed by the before/after. A
plausible reading is that an `-importPlatform`-installed runtime already has a sealed `.dmg` at
`/Library/Developer/CoreSimulator/Images/<UUID>.dmg` to hand out, while a MobileAsset-backed one has
to be repackaged with its restore metadata — but that is a story, not a finding.

**Not tested:** tvOS 26.5 was also `-importPlatform`-installed (2026-09-07T21:36,
`evidence/e11-import-AppleTVOSSimulatorRuntime_Cryptex-…txt:2`) but was never re-exported afterwards,
and that runtime is now gone — it is the one whose abandoned dyld cache F10 is about.

**Why it matters.** A Runtime Library is not a directory of `.dmg` files, and the `.dmg` case is the
*unusual* one — it exists here only because that runtime had already been through an export/import
cycle. `RuntimeOperations.library(at:)` already resolves a `.exportedBundle` to its inner image, so
`installer(for:in:)` matches it and the `hdiutil imageinfo` gate in `runtime offload` reads it
(verified: UDIF lzfse, CRC32, exit 0, for both). Anything else that assumes a flat file — a copy, an
integrity check, a byte-total verification — breaks on half the runtimes on this machine.

**The two sizes are not the same measurement.** `.dmg` uses `attributesOfItem[.size]` (logical);
`.exportedBundle` uses `DiskUsage.measure(...).allocatedBytes`. Both render a number, but they are
not comparable, and the same field feeds the `sizeBytes > 500_000_000` sanity gate in
`installer(for:in:)` and will feed any future byte-total verification. Worth reconciling before it
is relied on. **[VERIFIED-BY-US]**

### F13 — a simulator runtime's *image UUID* is not stable across an offload/import round trip

Measured 2026-09-09 (evidence:
`evidence/f13-offload-import-device-return-macos26.6.2-25G83-xcode26.5-x86_64.txt`). The iOS 26.5
runtime offloaded as image `34AF883C-5859-4A52-BA30-1BCB0A577DD2` came back from the same installer
as `99ABCCEF-23E0-461E-BE5B-CC7E85F8542B`. Same platform, version and build; different identifier.

`simctl runtime list`'s identifier is a **per-installation image id**, not a durable name for the
runtime. Anything that has to survive a round trip must key on `runtimeIdentifier`
(`com.apple.CoreSimulator.SimRuntime.iOS-26-5`) instead. The offload journal originally recorded only
the image UUID, so matching an installer to the devices it could restore would have broken after
exactly one cycle — the record would name an image that no longer exists.

**Device return replicated, and its granularity pinned.** Importing only iOS returned both iPhones to
`Shutdown` with their data (3.7 GB and 4.3 GB), automatically and with no manual recreation, while
the Apple Watch Ultra 3 — which needs `watchOS-26-5`, still offloaded — correctly stayed
`unavailable` with its 1.2 GB intact. Availability tracks the specific runtime, not "an import
happened". Import peak was 9 GiB for a 9.9 GB image (~0.9×), consistent with E11.

Still **one configuration**: macOS 26.6.2 / Xcode 26.5 / Intel, same-version re-import. Cross-version
import, Apple Silicon, and watchOS/tvOS device return remain untested. **[VERIFIED-BY-US]**

### F14 — `/Library/Developer/CoreSimulator/Images/` refuses file *creation* to root, with no SIP marker

Observed 2026-09-09 during the first E4b attempt. A plain `cp` as root:

```
cp: /Library/Developer/CoreSimulator/Images/images.plist.xcv-restore: Operation not permitted
```

The directory is `root:admin 755`, carries **no BSD flags** (`ls -lO` → `-`), has **no ACL**
(`ls -lde` shows none), and `/Library/Developer/CoreSimulator` is **absent from
`/System/Library/Sandbox/rootless.conf`** — which lists only `/System/Developer`. A sibling
root-owned directory under the same parent (`Profiles/`) shows the identical metadata.

This is the **same signature as the runtime Inbox** (2026-09-06 note in F1), where root deletion was
refused three times with `Operation not permitted` and `chflags`/`lsof` explained nothing. Two
different paths under `/Library/Developer/CoreSimulator`, both protected by a mechanism that leaves
no trace in the POSIX or SIP metadata a reasonable check would consult.

**Consequences already felt.** The E4b script wrote `images.plist` through a temp-file-plus-rename,
which is the standard way to make a config edit crash-safe. That is simply not available here, so
the edit and its restore are both in-place, and the protection against a truncated plist has to come
from a backup stored *outside* the directory plus a post-restore hash check. Any future code that
assumes it can stage a file in the secure storage area — the obvious shape for "verify, then swap
in" — will fail the same way.

**What it says about relocation.** CoreSimulator's secure storage area resists modification by root
without announcing itself. That is a design signal, not a proof, but it points the same way as
ADR-0004: the system means to keep runtime images somewhere it controls. Whether root can still
*overwrite* the existing `images.plist` in place — a different operation from creating a file — was
not established; the run aborted before reaching it. **[VERIFIED-BY-US]**

### F15 — `simctl runtime unmount`/`delete` take the image UUID, not the runtime identifier

`simctl runtime unmount com.apple.CoreSimulator.SimRuntime.watchOS-26-5` fails with "No runtime disk
images or bundles found matching …"; `simctl runtime unmount 28793F5D-…` succeeds. The help text
says `unmount <identifier>` for both verbs, and "identifier" there means the per-installation image
UUID that `simctl runtime list` prints — which F13 already showed is **not stable across an
offload/import round trip**. So any code that stores a runtime reference for later use must record
`runtimeIdentifier` and resolve the image UUID at the moment of use, never the other way round.
`simctl runtime scan-and-mount` remounts what `unmount` released. **[VERIFIED-BY-US]**

### F16 — `images.plist` is writable by simdiskimaged and by nobody else, root included

Measured 2026-09-09 (E4b, evidence
`evidence/e4b-images-plist-refuses-root-macos26.6.2-25G83-xcode26.5-x86_64.txt`). Root, on an
existing `root:wheel 644` file, opening `/Library/Developer/CoreSimulator/Images/images.plist` for
writing gets `[Errno 1] Operation not permitted`. Creating a *new* file in the same directory is
refused identically (F14). No BSD flags, no ACL, absent from `rootless.conf`.

**And yet the file changes.** `lastStateChangeAt` advanced to 23:25:34 — after the backup at
23:24:30 — because the run's own `simctl runtime unmount` made simdiskimaged rewrite it. So this is
not immutability; it is *"only the entitled daemon may write here"*, enforced by a mechanism that
leaves nothing in the metadata a reasonable check would consult. Together with the Inbox EPERM (F1)
that is three observations of one mechanism across two paths.

**This closes the relocation question, and earlier than H6 does.** ADR-0004 demoted canonical mount
because removable-device sandbox restrictions would follow the volume. This is a blocker upstream of
that: you cannot point CoreSimulator at an external image at all, because you cannot write the
database that holds the pointer, at any privilege a product may use. H9 ends split — the seal
survives relocation (E4a), and CoreSimulator cannot be made to use the relocated copy (E4b). The
Runtime Library workflow is not the pragmatic compromise; it is the only door left open.
**[VERIFIED-BY-US]**

## Survey after E4 — what relocation avenues are left, 2026-09-09 (E14a)

All of §F17–§F21 come from one read-only pass, `scripts/experiments/e14a-device-set-static.sh`,
evidence `evidence/e14a-device-set-static-macos26.6.2-25G83-xcode26.5-x86_64.txt`. Nothing was

### F17 — the Xcode 26 IDE *does* have a custom-device-set code path, and it is a user default

§F2 records, on one 2022 forum thread and tagged **[COMMUNITY-REPRO]**, that `simctl --set` has
"no evidence the Xcode IDE run-destination picker honours it". **That claim is now contradicted by
Xcode 26.5's own binary.** In `IDEiOSSupportCore` — the plug-in that owns simulator device
discovery — `-[DVTiPhoneSimulatorLocator startLocating]` does:

```
[[NSUserDefaults standardUserDefaults] dvt_filePathForKey:@"DVTSimulatorSetLocation"]
    nil      → [SimServiceContext defaultDeviceSetWithError:]      "Creating/fetching default SimDeviceSet"
    non-nil  → [SimServiceContext deviceSetWithPath:<pathString> error:]
                                                                   "Creating/fetching temporary SimDeviceSet at: %@"
    then     → -[DVTiPhoneSimulatorLocator _startLocatingDevicesInDeviceSet:]
```

The selector sequence is reproduced in the evidence file by resolving `__objc_selrefs` and
`__cfstring` against the x86_64 `__text` of the shipped binary. `DVTSimulatorSetLocation` is the
only string of its kind in the whole of `Xcode.app` (a full Mach-O sweep found exactly one binary),
`DVTiPhoneSimulatorLocator` is the only simulator device locator Xcode has, and it is what feeds the
run-destination picker. The key is unset on this machine.

**What this is and is not.** It is [VERIFIED-BY-US] that the code path exists, that it is selected
by a `NSUserDefaults` key, and that the key's name is `DVTSimulatorSetLocation`. It is **[UNKNOWN]**
whether the picker actually repopulates — a static read cannot show that, and it cannot show which
*domain* each client resolves `standardUserDefaults` to. That matters most for `xcodebuild`, which
has **no `--set` flag at all**: a non-bundled tool's standard domain is not obviously
`com.apple.dt.Xcode`, so the key may be invisible to it. E15 tests both domains.

Two further cautions the same evidence supplies:

- The IDE's own log string calls it a **"temporary"** SimDeviceSet. Together with Simulator.app's
  second key `TestingDeviceSetPath` and the class `DVTTestingiPhoneSimulator`, the intended audience
  looks like test infrastructure, not permanent relocation. That is a design signal, not a finding.
- **Nothing in `IDEiOSSupportCore` mentions `DeviceSetPath`.** Simulator.app reads its *own*
  `DeviceSetPath` / `TestingDeviceSetPath` defaults and calls `deviceSetWithPath:error:` itself, and
  Xcode does not pass the set through when it launches the app. So the two are configured
  independently, and the plausible failure is **silent split brain**: Xcode driving one set while
  the visible Simulator window shows another. Under rule 6 that is worse than not working.
  **[VERIFIED-BY-US (static)]**

### F18 — most of the device set is not user data: ~70% is cache, log and on-demand asset

`~/Library/Developer/CoreSimulator/Devices` is 9.1 GB here across **three** devices with data. The
composition, measured per device:

| | iPhone 17 Pro Max | iPhone SE (3rd gen) | Apple Watch Ultra 3 |
|---|---|---|---|
| total | 3.7 G | 4.3 G | 1.2 G |
| `data/Containers` (the actual app data) | 332 M | 192 M | — |
| `data/Library/Caches/com.apple.containermanagerd/Dead` | 998 M | 676 M | — |
| `data/private/var/MobileAsset/AssetsV2` | 1.3 G | 1.8 G | 161 M |
| `data/var/db/diagnostics` (unified log store) | 426 M | 286 M | 502 M |
| `data/var/db/uuidtext` (log symbolication) | 163 M | 146 M | — |

The single largest item on the machine's *user-owned* developer storage is not an app, a build or a
runtime: it is `com_apple_MobileAsset_UAF_Siri_Understanding` at 650 MB **inside one simulator**,
with `LinguisticData` (264 MB) and `ActivityChallengeAssets` (206 MB) behind it — speech and
intelligence models the simulated OS downloaded on demand. `containermanagerd/Dead` is the graveyard
of deleted apps' containers.

Roughly **6.5 GB of the 9.1 GB is regenerable**, against ~0.5 GB of real app containers. This
reorders the whole question: **relocating the device set moves ~9 GB but only ~2.6 GB of it is
durable, while cleaning it returns ~6.5 GB today with no new mechanism at all.** The catch is that
the caches come back — a cleaned device re-downloads assets on its next boot — so this is recurring
reclamation, not a one-off, and it must be presented that way.

Apple's supported instrument for the whole lot is `xcrun simctl erase <device>`, which also destroys
`data/Containers` and so falls under rule 5 (explicit user intent, per device, never automatic).
For the log store alone there is a *documented* narrower verb: `man log` defines `log erase --all`
("Deletes main log datastore, and inflight log data as well as time-to-live data"), which can be run
inside a device with `simctl spawn`. **Not yet reproduced by us.** The first product move here is
none of these: it is to **report** the split, which `scan`/`doctor` can do today and no competitor
does. **[VERIFIED-BY-US]** for the measurements; **[UNKNOWN]** for what any cleanup verb actually
returns and how fast it regrows.

### F19 — `simctl create` documents a *path* as a runtime specifier

`xcrun simctl help create` on Xcode 26.5, verbatim:

```
<runtime id>  A valid and available runtime. ...
              Examples: ("watchOS3", ..., "/Volumes/path/to/Runtimes/watchOS 3.2.simruntime")
```

Apple's own help text offers a `/Volumes/...` path to a `.simruntime` bundle. That is the legacy
pre-Xcode-14 packaging, and this machine has no `Profiles/Runtimes` directory at all (F10) — but
E4a showed that the vault's sealed image **attaches from the external USB volume as a normal user
and exposes `iOS 26.5.simruntime` inside**. So there is an untested route to a device backed by a
runtime whose bytes are external that never touches `images.plist` and never needs root, which is
exactly the wall F16 hit. `simctl help clone` likewise documents a `[<destination device set>]`
argument, i.e. a supported way to *move* an existing device between sets.

Do not over-read this. `simctl create` is undocumented outside its own `--help`, the path form may
be dead code kept for compatibility, and a runtime accepted this way may still be registered
internally on first use. But it is a concrete, cheap, unprivileged probe against the exact barrier
E4b found, and it has never been run. **[APPLE-DOC (help text)] / [UNKNOWN] (behaviour)**

### F20 — FSKit's mechanism is documented and fits; its delivery is what is broken

H7 was deferred partly for want of a mechanism. Apple documents one: **"Building a passthrough file
system"** — "exposes an existing path as its own file system" — with sample code, and
`FSPathURLResource` lets a file system be instantiated from a path rather than a block device
(https://developer.apple.com/documentation/FSKit/building-a-passthrough-file-system). `mount(8)` on
this machine documents `-F` ("Forces the file system type be considered as an FSModule delivered
using FSKit"), `FSKit.framework` is present, and `fskitd` / `fskit_agent` / `fskit_helper` are
installed. **[APPLE-DOC]**

**And FSKit is orthogonal to F16, which is the interesting part.** F16 says the *pointer* in
`images.plist` cannot be rewritten. A passthrough file system does not rewrite any pointer: it
changes what an existing path resolves to. That is the one shape of relocation the E4b barrier does
not, by construction, forbid.

Against that: third-party FSKit extensions are reported broken on macOS 26.1/26.2 — `fskitd`
rejecting unprivileged clients with `com.apple.extensionKit.errorDomain Code=2` and "entitlement
no", reproducing on Apple's own sample; the issue was closed "not planned" in Dec 2025 with fixes
said to be pending (https://github.com/andrewgazelka/loaf/issues/1). A separate DTS thread has
Quinn diagnosing a **deadlock in `fskitd`** for the passthrough sample, cleared by a restart, with
internal bug r.172914665 (https://developer.apple.com/forums/thread/819160). Status on **26.6.2 is
untested by anyone we can find.** The entitlement `com.apple.developer.fskit.fsmodule` remains
required and its approval process undocumented.

So H7's blocker moves from "no mechanism / unclear fit" to "the mechanism is documented and fits;
the platform delivery is unreliable and the entitlement is a business gate". It stays R&D, but it is
now the *only* live path to canonical relocation of anything under `/Library/Developer`.
**[COMMUNITY-REPRO]** for the breakage, **[UNKNOWN]** for 26.6.

### F21 — the Locations defaults keys are current on Xcode 26.5, and one is live on this machine

§F2 flagged `IDECustomDerivedDataLocation` / `IDEBuildLocationStyle` as a 2016-era source, "verify
empirically". `IDEFoundation` in Xcode 26.5 contains, as literal strings:
`IDEBuildLocationStyle`, `IDESharedBuildFolderName`, `IDECustomDerivedDataLocation`,
`IDECustomBuildProductsPath`, `IDECustomBuildIntermediatesPath`,
`IDECustomDistributionArchivesLocation`, `IDECustomCompilationCacheLocation`,

Two of those are new to this document and both are relocation surface Apple exposes in

a sandboxed process from the volume" is an assumption about a rule we cannot state. It is testable

Worth noting for the ranking: on *this* machine the point is moot — DerivedData is 28 KB and there

## Per-device regenerables, 2026-09-13 (catalogued into `scan`/`doctor`)

### F22 — the `Dead` containers are superseded app installs, and they are the fastest-growing thing on the machine

`data/Library/Caches/com.apple.containermanagerd/Dead` was 836 MB on 2026-09-09 and **2.1 GB on
2026-09-13**, across two devices — it roughly tripled in four days while `MobileAsset` held flat at
3.3 GB. F18 measured the split; this is what is inside it.

Each entry is a `temp.XXXXXX` directory holding exactly one UUID container, and that container is an
**app bundle container**, not user data: `.com.apple.mobile_container_manager.metadata.plist` reads
`MCMMetadataCreator = com.apple.installd`, `MCMMetadataContentClass = 1`, with the bundle id of the
app. On this machine all 27 entries are the same app — a test rig's `com.mysmoke.app` — at ~125 MB
each, of which 57 MB is the app's `.debug.dylib` and 34 MB a bundled watch app. So the growth rate is
not exotic: **every install of a changed app leaves one of these behind**, which means the category
grows with ordinary development and grows fastest for exactly the workflow Xcode encourages (build,
run, repeat). A developer iterating on a 125 MB debug build pays ~1 GB per eight runs.

**No official command reclaims it.** `simctl`'s full verb list has `erase` (destroys the device's
entire data volume, including `data/Containers`) and `delete` (destroys the device). Nothing narrower
exists. Any surgical reclaim would therefore be a filesystem deletion of our own design.

**A booted device reaps them itself, on a rolling age-based schedule.** The first attempt to measure
this was contaminated and discarded — the probe booted a device the machine's owner was concurrently
driving with `xcodebuild test`, so the entries that appeared mid-window were the test's and the size
change was not attributable. What made the answer legible anyway was the *control*: the second
device was never booted.

| device | before | ~2 h later | state through the window |
|---|---|---|---|
| iPhone 17 Pro Max | 15 entries / 1.5 GB | **3 entries / 306 MB** | booted |
| iPhone SE (3rd gen) | 12 entries / 676 MB | **12 entries / 676 MB** | shut down |

Every entry that predated the boot is gone — including the four the concurrent test created at
19:06, which is the direction that matters, since a test run only ever *adds* to this directory. The
shutdown sibling did not change by a single byte. `containermanagerd` inside the device logged
nothing about it at the default log level.

**The cadence is not what it first looked like, and the first draft of this finding said so wrongly.**
The three survivors are timestamped 19:16, 19:20 and 19:27, which read at 19:30 as "only entries
younger than ~10 minutes survive" — a rolling age-based reaper. A re-measurement an hour later
falsified that: the same three entries were still there, byte for byte, untouched. So the sweep was a
single bulk event that removed everything predating it, not a steady trickle, and what triggers it is
unknown — plausibly the end of the test run, an install/uninstall event, or a pressure signal, none
of which this run can distinguish. The honest claim is **"booting gets it collected"**, not "booting
collects it within N minutes", and the product copy was corrected to match. Worth recording as a
mechanism: two consecutive measurements of the same directory supported two different models, and
only the second measurement showed which one to discard.

This is an observation with a control rather than a controlled experiment, and the residual
uncertainty is narrow and named: it cannot separate containermanagerd's own timer from something
`simctl` or the test harness triggered. It does not need to. **The operational fact is settled: this
directory drains on its own whenever the device runs.**

**Which inverts the product conclusion, and improves it.** The category is not "unverified, so do not
offer" — it is "verified to self-heal, so *never* offer, and say why". A large number here does not
mean a leak waiting to be reclaimed; it means a device that has not been booted lately. `doctor` now
carries that as its remediation: boot the device, or delete the device with `simctl delete <udid>` if
it is one you no longer want. Deleting these files ourselves would buy the user nothing they were not
already going to get, while racing the daemon that owns the directory on any device that is running.

The same does not transfer to the other two per-device categories, and the catalog notes say so
per entry: `MobileAsset` is a write behind `mobileassetd`'s own bookkeeping (`AssetsV2/analytics`
plus per-type state) — the F16 mistake one layer in — and the log store has a documented narrower
verb (`log erase --all` via `simctl spawn`) that we have not reproduced. Both ship reported-only with
no remediation offered, which is the honest rendering of not knowing.

**[VERIFIED-BY-US]** for the container contents, the metadata, the sizes, the absence of a narrow
`simctl` verb, and the reaping-on-boot behaviour with its shutdown control. **[UNKNOWN]** for which
component performs the reap and on exactly what schedule — neither of which changes what the product
does, since the answer either way is "leave it alone".
