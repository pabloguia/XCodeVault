  Prediction held. No device was recreated by hand; none lost data; the Watch correctly did

THE FINDING THAT WAS NOT PREDICTED — the image UUID is not stable across the round trip
  offloaded: 34AF883C-5859-4A52-BA30-1BCB0A577DD2
  imported : 99ABCCEF-23E0-461E-BE5B-CC7E85F8542B

  The runtime is the same platform, version and build (iOS 26.5 / 23F77) and the devices bind
  to it correctly, but `simctl runtime list`'s identifier is a *per-installation* image id, not
  a stable identity for the runtime.

  This matters directly: the offload journal originally recorded only that UUID. Matching an
  installer to the devices it can restore by image UUID would therefore fail after exactly one
  round trip — the entry names an image that no longer exists. `runtimeIdentifier` is the
  stable key, which is what the journal now records in `detail` and what
  `Doctor.checkUnavailableDevices` matches on.

SECOND-ORDER CHECK — the rule's own behaviour on live data after the import
  `xcodevaultctl doctor` now reports 1 unavailable device (was 3), and its remediation refers to
  "a runtime" (singular): the iOS offload entry is excluded because a completed `runtimeImport`
  for the same installer follows it, leaving only the watchOS one. The stale-entry filter works
  against real journal data, not just fixtures.

SCOPE — what this does and does not establish
  Two observations, ONE configuration: macOS 26.6.2 / Xcode 26.5 / Intel, iOS 26.5, re-imported
  at the SAME version. Nothing here says anything about a cross-version import, about Apple
  Silicon, or about watchOS/tvOS device return — the watchOS installer is still on the vault and
  that case remains untested.
