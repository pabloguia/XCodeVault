## step 5a — create a new folder (Files > Browse > On My iPhone > "..." > New Folder)
RESULT: SUCCESS. No error dialog. The folder appeared as "untitled folder", 0 items, with the
name in inline-rename mode, and the container footer changed from "On My iPhone is Empty" to
"1 item". It persisted after leaving and re-entering the view.
Confirmed on disk, through the symlink:
  .../Devices/<probe>/data/Containers/Shared/AppGroup/8325E71A-.../File Provider Storage/untitled folder
NOTE ON METHOD: the first tap on "New Folder" produced no folder and the menu simply closed.
This looked like a reproduction of the reported failure, but it was an artifact of the
automation, not of the product: the Simulator window was not the frontmost macOS window, so its
first synthetic click is consumed as a window-focus click. The same tap repeated immediately
afterwards created the folder. Every subsequent interaction in this run showed the same
one-eaten-first-click pattern on each new UI state. Recorded here because a less careful run
would have logged a false positive for H5.

## step 5b — share a photo and save it into Files (Photos > image > Share > Save to Files)
RESULT: SUCCESS. The share sheet opened normally and listed the full action set; "Save to Files"
was present; the document picker opened on "On My iPhone" with "Save as IMG_0002"; tapping Save
dismissed it with no error dialog.
Confirmed on disk, through the symlink: File Provider Storage/IMG_0002.JPG, 2,567,402 bytes.

## step 5c — save a file from Safari
RESULT: SUCCESS, via download. Two variants were exercised:
  (1) Sharing a plain-text page rendered inline offered no "Save to Files" entry — only
      URL-level actions (Add to Favorites / Find on Page / Markup / Print). This is ordinary
      iOS behaviour for a page share, NOT a failure: Safari shares the URL, not a file.
  (2) Serving the same content as a .zip from a local HTTP server on the Mac (127.0.0.1:8099)
      produced Safari's "Do you want to download ...?" prompt; Download completed and the
      download badge appeared in the address bar.
Confirmed on disk, through the symlink:
  File Provider Storage/Downloads/e9-safari-download.zip
The guest had no route to the public internet during this run (an earlier attempt to load
example.com rendered blank), which is why a local server was used; this does not affect the
claim under test, since the write path into Files is identical.

## guest log check during the Files interactions
A `simctl spawn <udid> log stream --level debug` capture (845,711 lines, not committed) was
scanned for FileProvider/sandbox/symlink failures. Findings:
  - Guest subsystems resolve paths through the symlink to /Users/<user>/CoreSimulator-real/...
    and operate on them successfully, e.g. MobileAsset "successfully locked SHORT-TERM" against
    .../CoreSimulator-real/Devices/<probe>/data/private/var/MobileAsset/...
  - The only "Operation not permitted" lines come from runningboardd (pid_resume / pid_suspend /
    Darwin GPU role changes) and kbd's memorystatus_control. These are ordinary Simulator noise
    on any device, unrelated to the symlink, and appear on non-symlinked runs too.
  - No sandbox denials and no FileProvider errors were logged.

## step 8 — FB12363725 opportunistic check (read-only; the wider ~/Library/Developer swap was
##          deliberately NOT performed — CLAUDE.md rule 7)
Both paired physical devices remained "available (paired)" in `xcrun devicectl list devices`
throughout, while only CoreSimulator was symlinked: an iPhone 17 Pro Max and an Apple Watch
Ultra 2. No "Preparing..." state and no DDI errors were observed. This is negative evidence for
the narrow case only; the report's own precondition (symlinking ~/Library/Developer itself) was
not reproduced and remains untested.
SCRIPT WORDING DEFECT (recorded for honesty): the automated check above prints "real directory
(as required)" for ~/Library/Developer/DeveloperDiskImages, but `ls` on the same line shows
"No such file or directory" — the path does not exist at all on Xcode 26.5 here. The `[ -L ]`
test is false for a missing path, so it falls into the else branch. Not a rule-7 violation
(nothing was symlinked), but the message is misleading and the check should test existence
first.
