### 3.6 — Licence, provenance, and what ships in the DMG

**L1. Apache-2.0 attribution for `swift-argument-parser` — FIX NOW (not a blocker).**
The brief assumed plain Apache-2.0 and treated this as publication-blocking. It is not. The
dependency ships Apache-2.0 **with the Swift Runtime Library Exception**, whose text explicitly
waives §4(a), §4(b) and §4(d) for code embedded into a binary by compilation. Independently:
§4(b) does not attach (the dependency is unmodified), §4(c) covers Source form only (object code
is what ships), and §4(d) is conditional on the upstream shipping a `NOTICE` file — it ships
none (`find -iname 'NOTICE*'` over the whole checkout returns nothing). Under a strict reading
that denies the RLE reaches a non-runtime library, the single residual obligation is §4(a), "give
recipients a copy of this License". Remedy is a `THIRD-PARTY-LICENSES.md` — deliberately *not*
named `NOTICE`, which is an Apache-2.0 term of art that would create a §4(d) obligation for this
project's own downstreams that it does not currently have.

**L2. The shipping claim is confirmed by inspecting the binaries, not the manifest.**
`nm -U .build/debug/xcodevaultctl | grep -c ArgumentParser` → 9119; the same over the app binary
→ 0; `otool -L` lists no ArgumentParser dylib, so it is statically linked.
`bundle-app.sh` copies the CLI into `Contents/MacOS/` unconditionally and the Homebrew cask
exposes it as `binary`. Nothing else third-party ships: one entry in `Package.resolved`, no
vendored directories, no Podfile/Cartfile/package.json.

**L3. Provenance is clean.** Every `mac-ssd-rescue` reference is nominative/interoperability use —
`Doctor.swift` builds a path to a directory *by name* and reports on it, the way antivirus names a
threat. The one quoted snippet in `PRIOR_ART.md` was diffed line by line against the fetched
upstream: three of its four lines are rewritten, the fourth is a generic `rsync` invocation, and
upstream carries no copyright header at all. Upstream is MIT, so MIT→MIT regardless.

**L4. `CONTRIBUTING.md` states no inbound licensing terms — FIX NOW.** Sharper than a generic
omission: ADR-0005 shows Apache-2.0 was considered *specifically* for its §5 inbound=outbound
clause "which would make external contributions unambiguous without a CLA", then declined with
nothing put in its place — while README and CONTRIBUTING actively solicit outside contributions.
This gets strictly more expensive with every merged PR.

**L5. Supporting findings (issues).** 0 of 50 Swift files carry a licence header (headerless is
the Swift norm at this size — the fix is to *record the decision*, not to add 50 headers);
`Package.swift` declares `from: "1.5.0"`, floating any 1.x into a signed notarized artifact;
`NSHumanReadableCopyright` holds the string `MIT License`, which is a licence name in a copyright
field; nothing in CI would notice a future dependency arriving without an attribution entry;
ADR-0005 reasons about Apache-2.0 obligations outbound only, never about the one it consumes.

### 3.2 — Architecture

**A1. The `runtime offload` transaction lives in the CLI, where no test can reach it — FIX NOW.**
`Sources/xcodevaultctl/M2Commands.swift:154-225` implements four guards, an `hdiutil imageinfo`
verification and three journal transitions inside an executable target. Every sibling verb had its
policy pulled into Core (`RuntimeOperations.preflightExport`, `preflightImport`, `delete`); there
is no `preflightOffload` and no `offload`. It is the most destructive verb in the product — it
deletes 5-25 GB against a copy — and it is the only one that is structurally untestable. This is
the `getgrouplist` pattern the project already paid for once, and `Package.swift` says so in a
comment.

**A2. Helper verbs are `private`, so the target created for testability does not deliver it —
FIX NOW.** `Sources/XCodeVaultHelperCore` exists for one stated reason, written in
`Package.swift` and in the file header: "so the verbs, the authorization gate and the path guards
can be tested". The authorization gate is tested. The verbs and path guards are not, and the
reason is structural rather than oversight: `HelperService.swift:139,165,191` declare them
`private func`, and `@testable import` reaches `internal`, not `private`. The refactor moved the
code into a testable target and then sealed it, while the header asserts otherwise to every future
reader.

**A3. `XcodeLocations.apply` takes a free-form defaults key from the CLI — FIX NOW.**
`Change.key` is a `public var String` written straight into `defaults write com.apple.dt.Xcode`
with no validation that it is one of the four keys the tool owns. Six call sites hold that rule by
discipline. It is a source-breaking change to a published library product, which is why it belongs
before the first push.

**A4. Each client composes the Doctor's rule families by hand — FIX NOW.**
`diagnose(report:) + diagnoseVault(report:)` appears identically at `XCodeVaultCTL.swift:68`,
`:88` and `XCodeVaultApp.swift:41`. A fourth rule family means editing three files, and missing one
silently drops findings with no compile error and no test failure.

**A5. ADR-0003 describes a helper dependency graph the code no longer has — FIX NOW.**
ADR-0003 says `XCodeVaultHelper` "depends on `XCodeVaultHelperProtocol` only"; `Package.swift`
has it depending on `XCodeVaultHelperCore` as well. The split happened on 2026-09-17 on a security
reviewer's recommendation and its rationale survives only in a `Package.swift` comment. This is a
genuine silent reversal, and it matters more than usual: ADR-0005 publishes the review discipline
deliberately, so a security reviewer arriving from the public repo reads ADR-0003 and forms the
wrong trust boundary. It is also the only durable home for the "nothing else may depend on
HelperCore" invariant, which no script enforces.

**A6. ADR-0001 and ADR-0002 are still marked `proposed` while the code implements them and
`CLAUDE.md` calls them non-negotiable — FIX NOW.** ADR-0001's gating condition ("accept after the
team confirms") cannot be met; there is no team. On a public repo, `Status: proposed` on an
implemented decision invites a contributor to reopen what is closed.

**A7. Structure findings left as issues.** `Doctor.swift` has a real seam at lines 471-941 — the
CoreSimulator cluster, 46% of the file, versioned by *Apple's* release schedule while everything
else is versioned by this project's; `MigrationEngine.swift` has one at 660-839, journal forensics
that migrate nothing and read only `[JournalEntry]`. Both are two-reasons-to-change splits, not
size complaints. Four missing injection seams were named with the specific failure each one blocks:
`isMountPoint` in `MigrationEngine` (the author already wrote "UNPINNED, knowingly" beside it),
the free-space guard, `XcodeLocations.preflightLocation`'s shadow-data check, and
`CleanExecutor.preflight`'s nested-mount-point guard.

### 3.3 — Apple platform

**P1. `xcodeIsRunning()` fails OPEN when the CLI runs without a GUI session — FIX NOW.**
`CleanPlanner.swift:166` uses `NSWorkspace.shared.runningApplications`, which is a LaunchServices
query scoped to the caller's Aqua session. A process without one — `xcodevaultctl clean` over SSH
— gets an empty array, the guard evaluates false, and DerivedData is deleted out from under a
build running in the console session. The audience for this tool is developers who SSH into a Mac
to free disk, so this is the ordinary path, not an exotic one. DerivedData is regenerable, so this
corrupts an in-flight build rather than losing data — which is why it is FIX NOW and not a
blocker. It is also the sole reason `import AppKit` sits inside a target `Package.swift` describes
as "the single shared domain layer. No UI".

**P2. The DMG is built from the un-stapled app, and the comment beside it claims otherwise —
FIX NOW.** `release.sh:18` creates the DMG from `$APP` before `$APP` is ever stapled; `:23` staples
the copy *outside* the DMG while the comment at `:20` says "staple both the dmg and the app inside
it". The app a user drags out of the shipped DMG carries no ticket, so first launch depends on an
online Gatekeeper check and is rejected offline.

**P3. Three disagreeing version strings, and `--version` never reaches the shipped app — FIX NOW.**
`ScanReport.current` is `0.1.0-dev`, `Info.plist` is `0.1.0`, the cask expects
`XCodeVault-0.1.0.dmg`. `release.sh` derives its version from `ScanReport.swift`, so a plain
release run produces `XCodeVault-0.1.0-dev.dmg`, which the cask URL will never resolve — and
passing `--version` changes only the filename, never `CFBundleShortVersionString`, so the
notarized app reports the wrong version in an already-distributed artifact.

**P4. ADR-0001 carries a consequence the code has since falsified — FIX NOW.** It says a 13.0
fallback floor "costs no additional API work, only testing". That is no longer true: `@Observable`,
`@Bindable` and `ContentUnavailableView` are all 14.0-only and load-bearing in the GUI.

**P5. What the pass verified as sound, and is worth recording.** The `@unchecked Sendable` count
is exactly as claimed (2 + 3) and four of the five justifications are still literally true. There
is no `@preconcurrency`, no `-suppress-warnings`, no `unsafeFlags`, no `#warning`, and no
`@available`/`#available` anywhere — and no post-14.0 API is used, corroborated by the import set
(the only frameworks linked anywhere are Foundation, SwiftUI, AppKit, Security, CryptoKit). The
helper-dependency invariant holds under mechanical parsing of `Package.swift`. `TEAMID_PLACEHOLDER`
is a genuine fail-closed control and was left untouched. Signing is inside-out with no `--deep` in
any signing command, hardened runtime and `--timestamp` on all three signatures, and
`--with-helper` defaults off. The SwiftUI main thread is clean — every entry point funnels through
`Task.detached`.

**P6. Issues.** The XPC client requirement pins Apple anchor, both Developer ID marker OIDs, team
OU and a closed set of two identifiers, but adds no hardened-runtime flag clause; `SMAppService` is
never actually called, so `SECURITY_MODEL.md` §Registration reads as shipped behaviour for code
that does not exist; the helper's only diagnostics are two `stderr` writes that under
`SMAppService` reach a sink no user can find; the two commands the issue template recommends
(`doctor`, `volumes`) are the *unredacted* ones, and `volumes` prints raw volume label and UUID —
the project built a tested redactor and then asked users to hand-scrub; `release.sh` proceeds with
an empty `VERSION` if its `sed` matches nothing; the CI lint step cannot fail (both arms of its
`||` are green, so a missing tool and real lint failures are indistinguishable from clean).

### 3.1 — Agentic engineering

**G0. The brief was wrong about two of its own claims, and the pass caught it.**
The brief asserted that `AGENTS.md` still lacks the `SESSION-HANDOFF.md` pointer `CLAUDE.md` has,
and that `.agents/skills/` is mentioned by neither entry point. Both are false: the pointer is at
`AGENTS.md:40-42`, structurally identical, and `.agents/skills/` is named at `AGENTS.md:31` and
`:44`. Under a normaliser written independently of the repository's own, the two files show **zero**
divergence beyond the three intended substitutions. What is true is narrower: it is `README.md`,
`CONTRIBUTING.md` and everything under `docs/` that never mention `.agents/`.

**G1. Safety rule 10 points at a section name that does not exist — FIX NOW.**
Both entry points say a strategy must "meet the Definition of Done in
`docs/product/NON_GOALS_AND_SAFETY.md`". That file's heading is
`## Definition of "supported" for any storage strategy`; the phrase "Definition of Done" appears in
it zero times. The term is load-bearing in eight other places including three source files, the PR
template and a reviewer agent. The brief listed this as one of the four drifts *already fixed* — the
file-level pointer was fixed, the section name was not, and `check-doc-mirror.sh` cannot see it
because both documents are identical and its existence check asserts only that the *file* exists.

**G2. Three enumerations in the always-loaded entry point understate the tree by roughly half —
FIX NOW.** `CLAUDE.md` says "H1–H9" where `HYPOTHESES.md` defines H1–H13; "E1–E11" where
`EXPERIMENTS.md` defines E1–E15 plus E18; and names three experiment scripts where
`scripts/experiments/` holds twenty. This is the most expensive class of entry-point error: it is
loaded every session and teaches a *smaller world than exists*, so an agent asked about E14c does
not know it is in scope.

**G3. `scripts/` is described in Layout by two of its five scripts, and the two CI controls are the
missing ones — FIX NOW.** `bundle-app.sh` and `release.sh` are named; `helper-invariants.sh` and
`check-doc-mirror.sh` are not — even though both run in CI and `helper-guard.sh`'s own header names
the former as "the control". The entry point advertises the packaging scripts and hides the safety
controls.

**G4. `check-doc-mirror.sh` normalises in both directions, which re-opens the hole it was written to
close — FIX NOW.** Its swap table maps `.codex/` and `.agents/` onto `.claude/` and applies that to

exist. Its own header already identifies this mechanism as the thing that hid the dead

**G5. Two structural blind spots the script cannot close by differing — ISSUE.** A pointer deleted

(`XCodeVaultHelperCore` missing from both Layout paragraphs) was. And root-level files are never
existence-checked: the path regex requires a `/`, so `` `STATUS.md` `` is never evaluated.

**G6. The Codex mirrors of the reviewer agents carry the prose but none of the enforcement.**
`.claude/agents/helper-security-reviewer.md` restricts tools to `Read, Grep, Glob` and three
read-only git verbs — it is *incapable* of editing what it reviews. The `.codex/*.toml` mirrors have
no tools key at all; independence is asked for in prose at
`.codex/agents/helper-security-reviewer.toml:4` ("You review; you never edit"). For the agent whose
subject is local root escalation, that asymmetry is the wrong way round. The pass classified this as
blocking; see the adjudication below.

**G7. `.codex/hooks/swift-format-lint.sh` reads a Claude-only variable — FIX NOW.** Byte-identical
mirroring produced a defect *because* it is byte-identical: line 8 passes
`--configuration "$CLAUDE_PROJECT_DIR/.swift-format"`, which is unset under Codex, so the hook lints
against `/.swift-format`, swift-format errors, `2>&1` captures the error into the output variable,
it is printed as if it were lint output, and the hook exits 0. A Codex contributor gets a confusing
error and no linting. This is the concrete cost side of the mirroring trade.

**G8. `swift-format-lint.sh` has a lower ceiling than the hook that was demoted for having one —

**G9. ADR findings, including the same silent reversal architecture found — FIX NOW.**
ADR-0003 is `accepted` and fixes the layout as "`XCodeVaultHelper` depends on

### 3.5 — Software quality

**Q0. The suite has no dead assertions, which is unusual enough to record.** Two independent
detectors, both positive-controlled: a brace-counting scan for test bodies containing no assertion
at all (zero hits across 14 files), and a grep for tautologies like `XCTAssertTrue(true)` (exit 1).
All 11 `XCTAssertNotNil` call sites were inspected individually and every one is on a genuine
optional. The 269 count reconciles with `grep -rc 'func test'`.

**Q1. The GUI's delete confirmation states a number larger than what it deletes — FIX NOW.**
`XCodeVaultApp.swift:231` titles the dialog `"Delete \(selection.count) item(s) permanently?"`
while `:234` deletes `plan.actions.filter { selection.contains($0.id) && !$0.requiresRoot }`. Select
a root-owned row alongside two user rows and the dialog says "Delete 3 items" while 2 are deleted.
The button is correctly disabled off the *filtered* set, so the unfiltered count leaks in exactly
one place — the number the user reads immediately before confirming a permanent deletion.

**Q2. The GUI is strictly more destructive than the CLI, with no way to say so — FIX NOW.**
The CLI exposes `--trash` (`M2Commands.swift:21`); `applyClean` constructs `CleanExecutor()` with
defaults, and the default is `useTrash: false`. The GUI always hard-deletes and offers no
equivalent.

**Q3. Three root-daemon verbs have zero tests behind a gate that is well tested.**
`doCreateVaultDirectory`, `doRemoveRegenerableSystemDirectoryContents` and
`doRemoveStrandedRuntimeDownload` have no test references at all (verified with a positive control
that returned 4 hits from a planted probe). The designed mutation — replacing the
`(created && st_uid == 0) || st_uid == callerUID` ownership guard with `true`, which would let an
admin have root `fchown` another user's vault root to them — is **predicted to survive**. This is
the same finding architecture reached from the other direction (A2): the gate is tested, the verbs
behind it are not, because they are `private`.

**Q4. The only pin on the abort/forget termination bound may not exist on CI — FIX NOW.**
`M3Tests.swift:392` is the sole test holding the bound that took five passes to get right, and it is
gated on `chmod +a "<user> deny delete"` succeeding (`:413`). That works here. Whether it works on a
GitHub runner is unverified — and if it does not, the test silently does not exist there, with
nothing turning red. Two more ACL-gated tests in `OwnershipAdviceTests` have the same exposure.

**Q5. The 20 `XCTSkip` sites classified.** Eleven are `getuid() == 0` guards on tests that simulate
permission failures with mode `000` — correct, and they fire neither here nor on a runner (which
runs as uid 501). Three are dead skips that can never fire anywhere. **Six cannot be ruled out on
CI**, and three of those are the ACL sites in Q4. None of the six is proven to fire; none is proven
not to. The structural fix is cheap and needs no hardware: have CI *assert* that the environment
supports what the skips need and fail if not, and fail if the skip count exceeds a committed
baseline. Today an environment change can delete tests from CI with nothing turning red.

**Q6. `COMPATIBILITY_MATRIX.md` does not overclaim, and the product side does not either.**
No row says "supported" (positive-controlled). Every strategy verdict is `probable` with the
Definition-of-Done gap named explicitly. `isExperimental` resolves to non-experimental for exactly
three categories, and all three are `.appleManaged` or `.neverMove`, so they qualify twice over — no
category with an actual relocation or cleanup strategy is marked verified. Rule 10 holds where it
matters. Three rows warrant demotion on evidence grounds: a `.verified` catalog status whose
evidence (F22) has no matrix entry at all; a verdict at line 275 that says the formula "generalizes"
from n=2 on one machine, where the adjacent line 219 correctly scopes the same claim to "on this
machine"; and a row whose evidence is "this session's transcript (no `.txt` evidence file written)"
in a document whose own header calls it an evidence ledger.

**Q7. CI: all five gates present, exit status propagates, and the fork-PR exposure is smaller than it
looks.** `continue-on-error` is absent (positive-controlled); `set -o pipefail` on the build and test
steps is load-bearing; all three scripts exit non-zero correctly, and `helper-invariants.sh` treats a
rule it cannot evaluate as a violation rather than a pass. A fork PR does get arbitrary execution on
the runner — that is inherent to building untrusted code — but there are no secrets referenced,
`GITHUB_TOKEN` is `contents: read` and read-only for forks regardless, and nothing publishes from
CI. The residual primitive is artifact poisoning: a fork can write anything into an evidence file
and have it uploaded under the repository's artifact namespace. **SHA-pinning the two actions does
not materially change this** given those constraints — worth doing because it costs one line each,
not worth treating as a publication gate. The control that does matter is a repository setting:
require approval for *all* external contributors, not just first-time ones.

### 3.4 — Code review for maintainability

**C1. `--profile safe|transparent|expert` appears in every command's `--help` and is read by nothing
— BLOCKS PUBLICATION.** `XCodeVaultCTL.swift:28-32` declares it on `GlobalOptions`, which is
`@OptionGroup`'d seventeen times, so ArgumentParser surfaces `--profile <profile>` on `scan`,
`doctor`, `clean`, `externalize`, `migration` and the rest. A grep over all of `Sources/` returns
exactly two lines for `profile`: the declaration and the enum. **Zero readers.** On a tool that
deletes files, `--profile safe` reads as a constraint on the invocation, and a user who sets it and
then runs `clean --apply` has been told nothing true. This is the brief's own blocking category — a
false claim on a surface a stranger reads first. It is also the only place in the repository using
the words "transparent" and "expert", vocabulary that survives from a design discussion and is
explained nowhere.

**C2. `doctor` reports a clean bill of health when it cannot read the journal — FIX NOW.**
`Journal.ReadResult` exists specifically to prevent this and says so: *"Silence from a journal that
could not be read must not be mistaken for a fact."* Exactly one consumer honours it — the
unavailable-device rule the comment names. Three siblings do the condemned thing:
`Doctor+Vault.swift:18`, `:83` and `:101` each `guard let … = try? … else { return [] }`, so an
unreadable journal yields no interrupted-migration findings, no leftover-partial-copy findings, and
no vault findings at all. `DoctorCommand.run()` exits 2 only on `.error` findings, so the command
whose entire job is to say what is wrong exits 0 and says nothing. The correct pattern is already in
the same codebase two files over (`Doctor.swift:276-281`, `:399-404` keep the Optional and map `nil`
to an `.unreadable` shape), which is what makes these read as missed rather than decided.

**C3. The two redactors diverge on the boot volume's bare label, and the header claims a parity that
is false — FIX NOW.** Run against a fixture volume named after a person, the shell `xcv_redact`
emits the label verbatim while `Redaction.swift` replaces it. `common.sh:184-187` redacts the boot
volume in its `/Volumes/` form and then `continue`s, skipping the bare-label rule; its comment
argues that word boundaries cannot save a label like `MacOS` because `/` is not a word character —
correct, but it never considered the lookbehind that the Swift side uses (`(?<!/)`), which protects
the bare label *and* still preserves `Contents/MacOS/`. Current exposure is nil only because this
machine's boot volume happens to be named `MacOS`; the risk is the next contributor whose volume is
named after them. `Redaction.swift:5-9` claims the two are "deliberately kept in step" and that
"every defect found in one has also been present in the other" — false as of today, and nothing
mechanically compares them.

**C4. A 15-line authorization contract in the root daemon is attached to the wrong function, and
duplicated — FIX NOW.** `HelperService.swift:35-49` is an essay on the authorization gate ending in
"**Fails closed.**"; line 50 begins a different doc comment in the same `///` block, so Swift and
DocC attribute the whole thing to `passwdLookup`, a two-line `getpwuid` wrapper that performs no
authorization. Eight substantive lines are byte-identical to the canonical copy at `:89-105` on the
real gate. This is the highest-stakes place in the repository for a doc/code mismatch: an
independent helper-security review is mandatory, and a reviewer reading top-down meets the security
contract bolted to the wrong symbol.

**C5. `removeStrandedRuntimeDownload` asserts a property nothing checks — FIX NOW by deleting it.**
The protocol comment says "Deletes one stranded runtime download"; the implementation validates the
*filename* and unlinks. There is no mtime check, no lock check, no size-stability check — **no
notion of "stranded" exists anywhere in the implementation**, and the failure string repeats the
claim. It has no client anywhere in the tree, its benefit is unproven (this project's own research
records macOS 26.5 refusing the unlink even for `sudo`), and it lives in a root daemon. Removing an
unreachable verb from an unshipped daemon costs nothing now; keeping it means the name has to be
defended in every future security review.

**C6. Two more comments that promise more than the code delivers — FIX NOW.**
`MigrationEngine.swift:594` says the bound needs "no prediction about deletability to **guarantee**
termination" — true only over a writable journal, and KNOWN-ISSUES already records that an
unwritable journal stops the failure count advancing. `TreeVerifier.swift:170` reports "content hash
differs" when the file could not be read at all; the guard is correctly fail-closed, only the
message is wrong, and for a multi-hundred-gigabyte non-regenerable migration that is the difference
between "check permissions" and "the drive is failing".

**C7. `CONTRIBUTING.md` tells contributors to update one of the two redactors — FIX NOW.** It names
`scripts/experiments/test-common.sh` only. This is the published instruction that manufactures C3.

**C8. Naming and dead code (issues).** `M2Commands.swift` and `M3Commands.swift` are named for a
milestone scheme that appears nowhere in README, CONTRIBUTING, CLAUDE.md or AGENTS.md — the docs use
"Phase 0…6" and never say M2, so the code's vocabulary is unrecoverable. Experiment IDs appear in
`--help` (`(E2)`, `(E11)`, `E8b`) with no pointer to where they are defined. `MountStatus.isNoBrowse`
is dead across the whole repository. `MigrationError` carries only a `String` while the engine holds
typed discrimination internally and flattens it at the public boundary — the named sufferer is
`Externalize.run()`, which cannot distinguish "retry" from "a partial copy is stranded and retry
will be refused".

**C9. What the pass checked and found sound.** Several claims that *could* have been false were
verified true: the `HelperContractTests` cross-module assertion, `helper-invariants.sh` really
running in CI, `VaultVolume.swift:96`'s "rejected by construction", `OwnershipAdvice.swift:114`'s
fail-open warning, `RuntimeOperations.swift:112`'s fail-closed claim, and README's four-surface
experimental labelling (GUI, CLI, catalog and docs all do label it). The friction flags
(`--i-verified-both-copies-myself`, `--i-confirm-deleting-non-regenerable-data`) are
self-documenting and need no change.

## Findings this review produced by its own work

These were not in any front's report. They came out of executing the fixes, and two of them
invalidate a baseline this review started from.

**S1. "`swift build` — 0 warnings" was an artefact of incremental compilation — FIX NOW, fixed.**
The baseline at the top of this document records `swift build` with zero warnings, measured the way
every previous session measured it. A `rm -rf .build && swift build` reports **four**:
`Scanner.swift:88` — a Swift 6 `SendableClosureCaptures` warning on a `var` captured by a
`DispatchQueue.concurrentPerform` closure, which is a real latent race the day anyone appends to
that array below the capture; and `VaultVolume.swift:158` — `result of 'try?' is unused`, on the
journal write whose own comment says it must happen. `swift build` re-emits warnings only for the
files it recompiles, so a tree can accumulate them while every local run reports clean. Both are
fixed; a clean build is now zero. The gate is now enforced rather than asserted: CI builds with
`-Xswiftc -warnings-as-errors`, which is the one place a fresh checkout makes this measurable.

**S2. The swift-format lint gate had never passed, and could not fail — FIX NOW, fixed.**
118 violations across 43 files. The CI step could not have caught them: both arms of its `||` were
green, so a missing formatter and real findings were indistinguishable from clean, and real findings
were downgraded to `::warning::` anyway. 114 of the 118 were mechanical (`AddLines`, `Indentation`,
`LineLength`, `OrderedImports`) and were fixed with `swift-format format -i`; the remaining four were
three `where_` identifiers renamed to `location` and one import ordering. The step now fails on a
missing formatter and fails on findings.

Formatting 43 files is exactly the change the brief warns about — a refactor that could lose
behaviour with nothing turning red — so it is proved rather than asserted: the 269 test names
captured before any file was touched were diffed against the 269 captured after, and the suite was
re-run. Both are recorded below.

**S3. A benchmark that could silently measure the wrong thing — FIX NOW, fixed.**
`DriveBenchmark.run` called `fcntl(fd, F_NOCACHE, 1)` and discarded the result — which is what the
`no-usage` warning in S1 was pointing at, one file over. If `F_NOCACHE` does not take, every number
the benchmark returns is the page cache's throughput rather than the drive's: wrong by orders of
magnitude, wrong in the flattering direction, and presented as a measurement. It now refuses rather
than reporting a good-looking number.

**S4. A dead root-file pointer in safety rule 10, found by the fix to the checker.**
Rule 10 in both entry points cited `` `COMPATIBILITY_MATRIX.md` `` as a bare filename; the file is at
`docs/architecture/COMPATIBILITY_MATRIX.md`. The original checker's path regex required a `/`, so it
never evaluated the reference. The rewritten existence check found it on its first run.

**S5. The leak scanner's own first version did not run.** Recorded above under the baseline: it used
`mapfile`, which the bash 3.2 macOS ships does not have. It failed loudly rather than silently, but
it is the same class as the three false "clean" scans §4 of the brief was written about, and it
happened inside the tool built to enforce that section.

## The two mandatory independent reviews

Repository rule: a change to the privileged helper goes to `helper-security-reviewer`, a change that
copies, moves, deletes or mounts data goes to `migration-safety-reviewer`, and **neither may be the
agent that wrote the change.** Both were dispatched against the working tree before anything was
committed. Both found things, and one of them found a defect in this review's own work that would
have shipped.

### Helper security — APPROVE WITH COMMENTS, all comments applied

The verb deletion was judged correct and complete: no dangling reference in `Sources/`, `Tests/` or
`scripts/`, the `@objc` protocol remains valid with a method removed, no client exists in either
direction so version skew is unreachable, and `helper-invariants.sh` derives its expected gate count
from the protocol rather than hardcoding it, so the check re-evaluates rather than going vacuous.
`TEAMID_PLACEHOLDER` confirmed untouched. Four findings, all fixed:

- **A rule-10 violation committed by this review.** One clause of the deleted duplicate comment —
  that group membership is used *rather than the Security framework's rights API, because
  `SECURITY_MODEL.md` forbids the null-authorization form outright* — existed only in the copy that
  was deleted. It was rehoused onto `isAdministrator`. This is exactly the failure mode rule 10
  describes, committed while applying rule 10, and caught only because the reviewer read both copies
  clause by clause.
- Shipping code still advertised the deleted verb: a catalog note said "removal is a helper verb in
  M3". A false product claim in a user-visible string.
- ADR-0006 — written earlier in this same session — named the deleted verb in the present tense, so
  it was being introduced already stale.
- The canonical comment said "these three verbs" where two remain.
- The *generalisable* half of the removed known-issue bullet still applies to the surviving cleanup
  verb, which deletes CoreSimulator caches with no in-use check. Re-added to `bundle-app.sh`.

On the two questions put to it: relaxing the verbs from `private` to `internal` is safe —
`XCodeVaultHelperCore` has exactly two dependents and `internal` is module-scoped — but **not
sufficient**, because both bodies resolve real absolute system paths, so a test calling them would
delete the real dyld cache. They need injected seams first. And it confirmed plainly that the
`createVaultDirectory` ownership guard is currently unpinned: replacing it with `true` passes every
gate. Both are recorded in KNOWN-ISSUES.

It also noted that `HelperIdentity.version` and `ScanReport.current` are two sources of truth for
"the version", which matters because the `version()` verb exists for skew checks. The module boundary
prevents expressing the agreement in code, so it is now a contract test —
`testHelperVersionMatchesTheProductVersion`, which is the one test name added by this review.

### Migration safety — REQUEST CHANGES, all changes made

Three blocking findings, and the first is the important one.

- **`xcodeIsRunning()` as rewritten was a regression.** Matching
  `/Xcode.app/Contents/MacOS/Xcode` looked tighter than the `NSWorkspace` bundle-identifier query it
  replaced. It is not: Xcode betas install as `Xcode-beta.app`, and anyone keeping several toolchains
  renames them. `NSWorkspace` caught all of those; the suffix match caught none. The change traded an
  unmeasured SSH false negative for a *certain* multi-toolchain false negative — and because
  `CleanExecutor.xcodeIsRunning` is also the default for `MigrationEngine.isXcodeRunning`, it
  weakened the guard immediately before source deletion. Now identified by `CFBundleIdentifier`,
  with the `.app/Contents/MacOS/Xcode` shape still required so a directory merely named `Xcode.app`
  cannot answer.
- **It was not fail-closed, despite its own comment saying so.** `proc_pidpath` returns 0 with
  `EPERM` for a process the caller may not inspect, so "the table listed but I read zero paths" was
  indistinguishable from "Xcode is not running" — the same failure one level down from the one the
  change was written to fix. Enumeration now returns `nil` rather than an empty array, and `nil`
  refuses.
- **No test covered any of the eight changes.** Five were added and each mutation-tested.

Non-blocking findings, all fixed: the registry do/catch **could not fire for the case it was written
for**, because `FileManager.contents(atPath:)` returns `nil` for a permission error exactly as it
does for a missing file — so an unreadable registry still returned `[]` and still reported a clean
bill of health; the `evidence: "Journal.ReadResult"` string cited a guarantee that call site was not
getting, since `entries()` discards `undecodableLines`, now surfaced as its own finding; the GUI's
Trash toggle made the journal say "freed" when the bytes had moved to `~/.Trash` on the same volume,
and carried none of the CLI's caveat; and two comments described code the same hunk had removed —
including the claim that `proc_listallpids(nil, 0)` returns a count, when it returns a byte count
with the kernel's own headroom already in it.

It accepted `TreeVerifier`, the `MigrationEngine` comment, `VaultVolume`, `Scanner` (confirming the
warning was hygiene, not a live race — `pending` is fully built before the concurrent block) and
`DriveBenchmark` (throwing is proportionate: `Result` has no caveat channel, so a degraded run would
return a page-cache number as a drive number). On the GUI it confirmed the count is now correct in
every path, and that defaulting the toggle to Trash changes no safety property for the worse.

**Both reviews are why the brief insists the author cannot review their own change.** Between them
they caught a regression, a fail-open, a fix that could not fire, and a rule-10 violation — none of
which any gate would have failed on.
